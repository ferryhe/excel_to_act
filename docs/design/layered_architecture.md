# Layered architecture and artifact boundaries

This is the normative map of implemented boundaries in this checkout. The README's Steps 0–5 describe a target workflow; they are not a claim that semantic analysis, generation, or numerical verification is complete.

## Layers

| Layer | Responsibility and inputs | Outputs | Must not do |
|---|---|---|---|
| **L0 — facts** | Read workbook/package bytes and record source-located facts. Inputs are `.xlsx`/`.xlsm` workbooks and their OOXML parts. | Manifest, inventory, raw source facts, logical-object and package-part ledgers, opaque records, and source-preserving handoffs. | Infer actuarial meaning, execute macros, recalculate formulas, or silently discard unreadable/unsupported content. |
| **L1 — deterministic views** | Select, organize, and trace L0 facts without changing their meaning. Inputs are validated Step 1 references, inventory, graph, and optional scope. | Step 2 index, stable workbook/sheet/region views, dependency evidence, and source-bound query/trace packets. | Add semantic conclusions, invent facts or locations, or claim runtime/formula verification. |
| **L2 — rule and semantic interpretation** | Apply explicit rules and request human decisions over L0/L1 facts. The implemented legacy path consumes inventory and graph; richer README Step 3 analysis is a target. | `ModuleClassification` and `ConfirmationTemplate` in the legacy path; future semantic contracts remain unspecified. | Mutate source facts, treat heuristics or hints as confirmed meaning, calculate formulas, or generate model code. |
| **L3 — numerical verification** | Compare a saved workbook calculation baseline with a distinct, actual recalculation result; later, compare generated code with the workbook baseline. | Planned #7 `ValidationReport` with source, coverage, status, tolerance, and coordinate-level differences. | Treat copied caches as an independent oracle, infer a missing result, or report a structural check as a numeric pass. |

### Dependency direction and cross-layer services

Data flows upward: **L0 → L1 → L2**; planned L3 consumes identified source facts and independent calculation results, and post-generation equivalence also consumes generated outputs. A layer may use contracts from `schemas/`; higher layers do not feed interpretations back into raw facts.

`interfaces/` adapts CLI input/output to workflows. `orchestrator/` coordinates the legacy multi-layer run. `store/` persists typed artifacts and lineage. `schemas/` holds contracts shared across stages. `plugins/` defines replaceable capability protocols. These are cross-layer services, not processing layers. Reporting spans phases: current renderers include the legacy `report/handoff.py` and Step 1/2 workflow handoffs. These services may depend on lower-level contracts, but must not introduce semantic or numerical behavior of their own.

## What runs today

There are two distinct entry paths:

1. **Legacy `excel-to-act inspect WORKBOOK --out DIR`:** `Phase1Orchestrator` reads L0 manifest/inventory, builds a deterministic formula graph, extracts VBA cell references, materializes them as L1 `GraphNode`/`GraphEdge` evidence, and merges those edges into `FormulaGraph`. It then applies rule classification, creates human confirmation questions, runs `verify_completeness`, and stores/reports the run. Thus rule classifications and questions already exist in this path. The classifier is heuristic; it is not the broader semantic analysis described by README Step 3.
2. **Human `step1` → `step2`:** Step 1 scans a directory, records per-source facts and preserved package parts, checks coverage/fidelity, and writes human/machine handoffs. It does not decide actuarial meaning. Step 2 indexes the handoff, validates referenced artifacts, compiles deterministic views and static dependency evidence, then supports bounded query/trace and reference validation. The Step 1 catalogue exposes optional graph/rule-classification tools, outside the Step 1 quality gate.

README Step 3's domain tags and structure contracts are a target beyond these current paths. The runtime classification contract is deliberately narrower: `ModuleCategory` values are `input`, `data_table`, `formula_block`, `lookup_block`, `output`, `presentation`, `external_dependency`, `unsupported_opaque`, and `other`; `ActuarialHint` values are `assumption`, `rate_table`, `cashflow`, `projection`, `output`, and `unknown`. Confirmation `question_type` is a string; current builders emit `category_override` (options are the category values) and `unsupported_feature_review` (options are `accept_record_only`, `manual_follow_up`, `ignore_for_phase1`). Do not add enum values merely to match roadmap wording.

## Contracts and stage artifacts

| Contract / producer | Inputs → outputs | Consumer and boundary |
|---|---|---|
| **#5 object coverage** — legacy `verify_completeness`; human Step 1 `check`/`coverage` | Legacy verifier: source OOXML, manifest, inventory, and graph → `CompletenessReport` (`completeness.json`). Its signature still accepts `classification`, but the function body does not read it. Human Step 1: fresh source scan plus candidate artifacts → `quality.json`, `logical_objects.json`, and `package_parts.json`, with measured counts/gaps/status. | Structural accounting gate before downstream handoff. Legacy `CoverageSummary` arithmetic alone is not independent discovery; #5 remains responsible for its accepted object-identity scope. This gate does not establish numeric correctness; L3 numerical verification remains separate and planned. |
| **#13 exact facts** — human Step 1 source scan | Workbook source XML and date system → `source_facts.json`; normalized `inventory.json` retains `CellInventory` raw value/formula text, formula attributes, OOXML type, cache text/availability, and date-system fields where measured. | Step 2 and later consumers use source-bound inventory/facts. A normalized display value is not a replacement for the raw source text. |
| **#14 deterministic views** — Step 2 `prepare` / `views.compile_views` | Standard `step2 prepare` validates the index and referenced artifacts, consumes validated inventory/manifest, supported optional control JSON (`checkbox_bindings.json`, `activex_events.json`), and optional scope; it derives a formula graph from inventory, passes it as `graph_overrides` to `compile_views`, and writes that derived graph into the reading package. An optional Step 1 `dependency_graph.json` is indexed/validated but is not the graph standard prepare uses to build reading views. Direct `compile_views` calls without an override may use a validated Step 1 graph. | `manifest.json`, `scope.json`, per-source `WorkbookView` files, derived `dependency_graph.json`, `dependency_audit.json`, `retained_dependency_cells.json`, and paired handoffs. Prepare turns supported control JSON into additional view records; indexed VBA handoffs are not used to construct the prepared graph or views. `step2 query`/`trace` produce an `EvidencePacket`; `views validate` checks response references and factual citations. These outputs prove source provenance, not recalculation or macro execution. |
| **#7 numerical verification (planned)** — no validator currently exists | Saved workbook cached values plus one distinct recalculation backend result → planned `ValidationReport` with coverage, result status, tolerance, and differences by sheet/address. | Pre-generation comparison checks the workbook baseline against an actual recalculation result. Post-generation code-equivalence is a separate future comparison of generated code against that baseline. Neither is implemented; structural PASS is not numeric PASS. |

The legacy per-workbook `artifact_index.json`, human Step 1 `batch_handoff.json`, human Step 2 batch `index.json`, Step 2 reading `manifest.json`, and source handoffs serve different contracts; do not conflate them. Step 2 accepts `step1.v1` and `step1.batch.v1` handoffs at its index boundary; it does not use the legacy artifact index. Local metadata dictionaries remain local where no cross-stage consumer needs a shared model.

## Deferred parser assessment (#10)

The current `openpyxl` plus OOXML path has direct work items for known ingestion gaps, and there is no concrete use case requiring Docling or markitdown integration now. The focused parser-fidelity comparison was not completed, the latest third-party versions have not been reassessed, and there is no evidence that their fidelity is disproven. Reopen #10 when a specific workbook use case cannot be served by current ingestion/views; then pin current versions and compare them against fixtures and the fidelity dimensions required by that use case. Compression research is outside this decision.
