# Step 6 model-conversion report contract

Each primary stage checkpoint produces paired machine-readable JSON and a human-readable Markdown handover. Step 6 produces the final conversion pair. JSON keeps accepted source facts, decisions, input files, coverage, comparison values, and original Step 3 questions. The existing report schema and workflow ledger remain authoritative for their respective evidence.

The reusable writing and review scaffold is packaged as the [Excel-to-Act Step 6 skill](../../src/excel_to_act/steps/step6/excel-to-act-step6/SKILL.md), with its report template in the skill's `assets/` folder. The CLI renderer remains the source of generated report structure and evidence.

Every Markdown handover starts with what the person is being asked to accept, purpose and scope, verified results or counts, limits and unresolved questions, links to the machine and human handoffs, and the next review action. The paired JSON and Markdown links and current workflow ledger should be easy to find. Technical appendix sections retain the detailed evidence and history. Keep raw JSON containers, hash strings and long technical ledgers out of the opening summary. Unknown facts remain “Not recorded” or unknown, never zero.

The Step 6 Markdown then leads with requested result values in accepted target order and a scoped conclusion. It explains intended use and scope, source inputs and assumptions, calculation order, module responsibilities, the conversion approach, reconciliation evidence, limitations, run instructions, and current acceptance state. It should explain scalar/vector/table totals, compact source-tab counts, field-group shapes and time alignment, and accepted recurrence notes from the design and catalog. Validation describes the recorded standalone Python artifact and native workbook oracle, plus coverage rows with explicit observed and required values when recorded. Partial extraction and actual unresolved business interpretations belong in the main limitations section. Detailed saved-input literals and source locations, formula evidence, hashes, review history, and prior option/question history belong in appendices.

For earlier stages, distinguish logical business inputs from physical cell coordinates; scalar, vector, table, source-raw, formula-derived external, adapter-metadata and pending inputs; and recurrence/module/path design from measured runtime behavior. Stage 3 is planning evidence, not calculation. Stage 4 smoke verifies the generated bundle only; it does not establish native Excel equivalence. Stage 5 reports requested targets separately from diagnostic intermediates when the bound design identifies them. If it does not, call the values named checks or leave their classification unrecorded. Keep inactive conditions separate from numerical routes or solver support. Technical artifact status such as `pass` or `ready_for_review` is not formal acceptance: `workflow.json` remains the current decision ledger.

Only use facts from accepted upstream artifacts. A linked input-boundary catalog may be read only when its recorded digest and source binding match; every catalog file used by Step 6 must appear in the Step 6 input-file list. Without a verified catalog, report catalog counts, shapes, axes, and source records as unavailable. Never replace missing facts with workbook-specific guesses. Preserve historical question text and dispositions in JSON while explaining later execution evidence separately. Keep inactive condition checks distinct from generated numerical routes and from any solver capability.

The generated report is ready for review and its JSON/Markdown pair is immutable after acceptance. By default, the Agent reviews the exact current pair first and the actual human responds second. A valid, currently registered scoped TypeSafe delegation can apply only to its authorized later stages; TypeSafe also follows Agent approval, while the Step 3 input-boundary checkpoint always requires actual human review. The linked workflow acceptance ledger (`workflow.json`) is authoritative for reviewer decisions; never edit the report to append approval state.

The report is a handover for the declared source case. Its structure borrows practical ideas from model-conversion lifecycle guidance, model-purpose and limitation disclosures, and documented validation comparisons. These references guide presentation; the report does not claim professional-standard compliance or actuarial certification.
