# Seven-stage conversion workflow

`step1 report --run RUN_DIR --out WORKFLOW_DIR` creates a native seven-stage workflow. Its stage producers and Agent/human review commands build the source-bound evidence. To use approved parent evidence, run `workflow attach --parent PARENT_DIR --out NEW_DIR --comparison COMPARISON.json --comparison-sha256 APPROVED_SHA256`. The parent `workflow.json` must use `schema_version: conversion.workflow.v1`, stage keys `1`–`6`, and `mode: production`, with current approved Stage 1–5 evidence. The CLI pins its exact manifest and the independently verified comparison digest, and rechecks source, artifacts, links, and approvals before delivery. Inherited Stages 1–5 are read-only. The attached root has its own Step 6 delivery and Step 7 report reviews.

Use the same workflow for each source, with Excel workbooks under `input/` and a new source-bound workflow directory under `output/`. Keep each workflow's targets, input catalog, scenarios, design and evidence together. Business names, worksheet coordinates, projection lengths, input counts, excluded calculations and expected values come from that source and the user's decisions. Never reuse another source's facts or approvals.

Each stage pairs its `agent.md` instructions with a real `tools/` CLI catalog. The packaged `stepN agent` command publishes the stage instructions; `stepN tools` publishes its current capabilities. The Agent selects tools for the current source, explores from source-bound evidence, checks outputs, and prepares the paired JSON and Markdown handoff. A generic Agent contract does not make the implemented formula subset, external-capture path or reconciliation adapter support every workbook. Check those limits for each accepted design and report missing support before execution. Store source-specific facts and decisions in the current workflow's bound reports, not in reusable documentation. The [Agent contract](design/generic_agent_contracts.md) explains this boundary.

## Stages and deliverables

| Stage | Work and CLI | Deliverables | Required review |
| --- | --- | --- | --- |
| 1 — Extract and preserve | `step1 convert`, `check`, `finalize`, `report` | Source copy, preserved package parts, inventories, handoffs, `import_checkpoint.json/.md` | Agent + actual human |
| 2 — Index | `step2 index`, `validate`, `report` | Navigation index, validated source/artifact references, `index_checkpoint.json/.md` | Agent + actual human |
| 3a — Confirm inputs | Static `step3` exploration, then `input-catalog` | Targets, scalar/vector/table input catalog, groups, source locations, raw/external boundaries, unresolved inputs, `input_boundary.json/.md` | Agent + actual human; this does not approve final design |
| 3b — Analyze and design | `source-trace`, `profile`, `plan`, `check`, `report` | Target/path/options ledger, variable/axis/recurrence design, semantic mapping/check, `analysis_design.json/.md` | Agent, then actual human |
| 4 — Generate code | `capture-external` when required by the supported modular path, `discover`, `plan`, `generate` | Bound external inputs, active source trace, implementation preflight, compact standalone Python, separate raw/external/metadata ledgers, source map, `generation_report.json/.md` | Agent, then actual human |
| 5 — Validate and reconcile | `validate`, `oracle`, `reconcile` | Isolated execution evidence, fresh native Excel capture, formula/value/error comparisons, coverage and tolerance results, `validation_report.json/.md` | Both technical checks pass, then Agent and actual human |
| 6 — Internal package | `candidate`, `deliver`, `revoke` | Exact versioned bundle, package JSON/Markdown pair, and separate internal delivery/readback record | Agent, then actual human decision on this exact pair |
| 7 — Final report | `report`, `skill`, `template` | `conversion_report.json/.md`: accepted artifacts, results, coverage, delivered code/run instructions, limits and open items | Agent, then actual human review |

Step 3 works backward from one value, several values, a column or a finite region. It confirms the input boundary before final design, then explains conditional paths, shared modules, scalar versus time-series variables, initialization, recurrence order, category axes, equation families and implementation options. Unknown closure or coverage stays unknown. Its static analysis and report commands do not calculate formulas, capture external values, generate runnable code or establish equivalence with Excel. The separate [finite-case route](cli.md#finite-case-preparation) verifies previously captured native evidence and calculates one source trace per approved request; it does not call Excel or create acceptance. After the current final design and exact input-boundary pair are approved, `step3 interface --workflow DIR` can write a deterministic, manifest-listed interface definition; it adds no Stage 3 revision or approval and leaves runtime readiness blocked while contract facts remain unknown.

Step 4 emits modular logical-variable code only, using the accepted design and source-family mappings. It requires the current semantic plan/check and implementation preflight; an incomplete design returns to Step 3 before any generation report or bundle is written. Use compact functions, aligned vector/category operations, ordered recurrence loops and reductions. Keep physical coordinates in the source map and adapter. Formula caches, active-trace calculated values and saved calculation results must not become raw model constants. Explicitly accepted formula-derived external inputs have their own capture and provenance. Unsupported active formulas, unresolved dependencies, cycles or missing adapter support block generation.

The standalone bundle runs without the workbook or project package. Review its manifest-listed files and source bindings rather than assuming a fixed file count or source layout. The isolated generation smoke proves execution only. Step 5 repeats isolated validation and independently compares against fresh native Excel results for the same source and declared scenario. The native tool uses a private read-only copy, disables macros/events, performs a full rebuild, and closes without saving. It requires Windows with Microsoft Excel. An oracle capture alone does not approve or advance Step 5. For the implemented `exact_cases` route, [validate and reconcile each of the 32 approved requests](cli.md#exact-case-validation), then run `step5 finalize-cases` with all 32 case receipts before reviewing the formal Stage 5 pair.

## Reviews, revisions and return routes

Native workflows use `workflow confirm` and `workflow reject` for their current Stage 1–7 JSON/Markdown pairs. Attached workflows keep inherited Stage 1–5 receipts as read-only provenance and review their own Stages 6–7. Stage 3 input-boundary confirmation is a separate Agent and actual-human decision.

Every stage binds its JSON/Markdown pair, revision, source hash and upstream inputs. Agent review precedes actual human review of the exact current pair. The workflow rejects a human approval until a matching Agent approval exists for that revision. Human decisions require an explicit user response. TypeSafe delegation and live TypeSafe review commands are disabled.

Run `workflow status --workflow DIR` before entering a stage and before each transition; verify the stage is currently permitted and required upstream decisions and artifacts are current. A successful draft or report command does not itself advance a stage. Standalone source-exploration APIs provide discovery evidence without creating workflow approvals. Use `workflow confirm` or `workflow reject` to record decisions, not a file edit. Ask the user when a target, scope, input kind, axis, units, or business interpretation remains materially unresolved; clarification is not a final stage decision. In native workflows, return to the stage responsible for the problem: source to Step 1, index to Step 2, scope/equations to Step 3, implementation to Step 4, and missing or failed comparison to Step 5. Stage 6 package or acceptance defects return to the responsible writable stage. Step 7-only report edits return to Stage 7. An attached workflow cannot return to inherited Stages 1–5. Correct its parent evidence and create a new attachment instead. Preserve the review audit trail. Changed source, inputs, reports or upstream revisions invalidate affected decisions and require new artifacts and reviews.

Each primary report starts with what the person is being asked to accept, its purpose and scope, key verified results, limits and unresolved choices, links to the machine and human handoffs, and the next review action. Detailed source evidence, question records and hashes stay available in the same report's appendix and JSON. A `pass` or `ready_for_review` value describes technical report integrity; `workflow.json` is the current acceptance ledger.

`workflow delegate` and `workflow typesafe` reject writes. Use the executable Agent-then-human review route; a recommendation or handwritten response cannot release a gate.

Step 6 stages the manifest-listed Step 4 bundle for internal permission and a version. Its review pair binds the exact package, current source and parent, interface, dependencies, fixed assets, accepted Step 5 report, and comparison for the exact smoke request. Agent review precedes a real human decision. `step6 deliver` then copies the same package, runs the delivered entry in isolation, compares readback, and records an effective internal delivery separately. A missing, rejected, stale, or altered approval/package/readback has no effective delivery. Retrying the same completed delivery is idempotent; package files and review records are retained. Runtime requests inside the approved domain do not require a new package approval; comparison proof must match the package's smoke request.

`workflow reject` at Stage 6 returns native workflows to Stages 1–6 or attached workflows only to Stage 6. At Stage 7, native workflows may return to Stages 1–7 and attached workflows only to Stages 6–7. Correcting an attached parent requires a new attachment.

Step 7 reports accepted source, design, implementation, validation, and internal delivery evidence. `step7 report` requires current Step 6 acceptance and delivered readback. It writes a report pair for review and does not itself approve it. A tested scenario does not imply all configurations, complete actuarial correctness, feedback solving, or GPU support.
