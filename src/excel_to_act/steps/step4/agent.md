# Step 4 Agent Contract: Generate the Approved Python Model

Step 4 emits code for the source-bound design accepted at Stage 3 and runs a bounded standalone smoke check. It does not compare results with Excel. It requires both current Stage 3 confirmations under the active workflow's review policy.

Write new instructions, report narration, and generated artifact prose in English. Preserve source values, formulas, identifiers, and immutable provenance verbatim. Only the repository-root `README.md` and `README.zh-CN.md` are approved bilingual documentation exceptions.

This contract is workbook-independent. Obtain all targets, inputs, dimensions, selectors, external boundaries, and equations from the accepted design and confirmed catalog. Do not reuse another workbook's source coordinates, parameter values, vector counts, or approvals. Inspect the tool and adapter capabilities for this design; missing support is a blocker, not permission to assume another model's layout.

Read `step4 tools` and the accepted Stage 3 design report. For a modular model, first run `step4 capture-external --workflow DIR` to capture only the approved formula-derived inputs, then `step4 discover --workflow DIR` to build a fresh active trace. Discovery uses source formula text and literals; it does not call Excel or read formula caches. Run `step4 plan --workflow DIR --implementation INPUT.json` with the Stage 4 implementation map supplied for the accepted design. The preflight rechecks the source, current Stage 3/capture/trace bindings, exact equation-family coverage, named references, metadata slots, and execution schedule. It compiles the projected functions and driver in memory and writes `implementation_plan.json/.md`; it does not run the model or advance Stage 4. Only after this preflight passes, run `step4 generate --workflow DIR`. Generation consumes the current preflight and discovery. You may pass `--trace TRACE.json` only for a hash-declared Stage 3 trace or an existing Stage 4 discovery trace. The command rechecks the source workbook, trace, formulas, and stage bindings before writing a new Stage 4 revision. It compiles the generated files and runs a bounded standalone smoke in a temporary folder without the workbook or project package; this is code-generation evidence, not a native comparison.

Review `generation_report.json/.md`, `model_manifest.json`, `model.py`, and `source_values.json`. For modular bundles, inspect `pricing.py`, `formula_families.py`, and `modular_runtime.py`; legacy bundles use `runtime.py`. Confirm that formulas are emitted as executable Python, the bundle imports only the Python standard library and its bundled runtime, and raw input values were reread from the unchanged workbook. Formula cells must not appear among raw inputs; saved formula-cache values must never be emitted as constants. Unsupported active formulas, cycles, external references, and unbound inputs must remain blockers.

## Modular-model acceptance

When the approved design requests a modular actuarial model, review the logical variables and equation families as well as execution. Scalars must remain distinct from time-projection series and age/category tables. A projection variable's initialization, recurrence segments, time lags, and source exceptions belong to one named variable. Emit compact functions, category operations, ordered recurrence loops, and root reductions. Function definitions must follow unique equation families rather than the number of spreadsheet cells.

Keep Excel coordinates in a separate source map and reconciliation adapter. Model equations should use logical variable names and indices. Formula-derived values remain calculations; neither a source cache nor an earlier model result becomes raw input. An unmatched required family must block generation rather than silently use a cell-by-cell fallback.

The modular emitter keeps business input variables, accepted external vectors, and adapter metadata in separate ledgers. Source coordinates remain in the adapter and source map; model functions use logical variables and indices. A derived variable may start from an accepted axis-metadata coordinate only when the semantic plan declares `source_role: accepted_axis_metadata`; that seed is hash-bound in the metadata ledger, initialized into its declared logical index, and excluded from raw business inputs. Ordinary source-backed initial conditions remain in the raw ledger. Formula-derived external vectors are an explicit reviewed exception: Stage 4 captures only the catalog-declared vector IDs, shapes, and shared key axis with a fresh macro-disabled native Excel rebuild, binds the source formulas and axes, and stores those values in a separate external ledger. Their upstream producer formulas stay outside the generated model. Formula caches and earlier model results are never inputs. Stage 5 captures a fresh native result and compares the external values, axis keys, source formula cuts, and active model formulas independently. Counts, lengths, keys, and source ranges come from the confirmed catalog. The current capture path requires a nonempty set of finite one-dimensional vectors sharing one declared key axis; unsupported boundary shapes or missing capture support require a revised implementation plan.

The approved scenario is fixed by the Stage 3 guards, including every declared raw input coordinate. Changing a guarded selector or raw input blocks the standalone run. A different source or scenario needs its own reviewed catalog, design, generated adapter, and reconciliation bindings. Check any workbook-specific assumptions in the available native capture and reconciliation adapters before promising reuse. A generated scenario bundle is not a general workbook converter.

Do not alter the source workbook or earlier stage artifacts. Do not claim that the smoke proves equivalence with Excel. Stage 5 repeats isolated generated-code validation and separately compares against a fresh native Excel result. After reviewing the exact report pair and bundle, record the Agent decision with `workflow confirm --workflow DIR --stage 4 --reviewer agent ...`. By default the human decision must follow an explicit user response. If this workflow has an active TypeSafe delegation, submit a current-bound request with `workflow typesafe --workflow DIR --stage 4 --request REQUEST.json`, then record an approval using its generated evidence file. If TypeSafe rejects, use `workflow reject --workflow DIR --stage 4 --reviewer typesafe --return-to 1|2|3|4 --message TEXT --evidence REVIEW.json`; never treat a hand-written packet as a live response. Stage 5 cannot start until both required confirmations are current.

A new explicit actual-human approval under a valid active TypeSafe delegation restores the required pair to Agent+human only for that exact current, unrejected JSON/Markdown pair and revision; it does not change the authorization or other stages. A rejection from any reviewer makes that revision ineligible for later approvals; create a replacement artifact and obtain new decisions.

## Shared workflow and decision order

Treat `input/` as the source Excel area and `output/` as the home for each new source-bound workflow and its reports. Start a new conversion from the current workbook and user request; never carry case facts or approvals from another workbook or run.

Read `stepN tools` and choose the existing actions that answer this case's open questions. Explore from the source and current bound evidence, inspect each action's checks and outputs, then prepare the paired machine-readable JSON and reader-facing Markdown handoff. Review all files named in the handoff and confirm their source and upstream bindings before asking for a decision. Do not continue when a required check fails or an input is stale.

Before entering a stage, run `workflow status` and verify that the stage is currently permitted and every required upstream decision and artifact is current. A successful tool check, report creation, draft CLI action, or clarification does not itself approve a stage or advance the workflow. Keep legacy standalone source-exploration APIs available for discovery; they do not create a workflow approval.

The default review order is Agent first, then the actual human. `workflow confirm` records approvals only; use the stage-specific `workflow.reject` command and its explicit `--return-to` route to reject. Record the Agent decision against the exact current JSON/Markdown pair with `workflow confirm`; present that pair and its practical limits to the user; record a human approval only after an explicit response. New TypeSafe approvals also require a current matching Agent approval. Use TypeSafe only under a valid, explicitly scoped authorization already registered for this workflow; never infer or transfer delegation. The Step 3 input-boundary checkpoint always requires an actual human decision.

Ask the user when target, scope, input kind, axis, units, or business interpretation is materially unresolved. Keep unknown facts marked as unknown; do not turn planning into measured execution or claim checks that did not run.

When a reviewer rejects a report at Stage 4, route it to the current or an earlier responsible stage with `workflow reject --workflow DIR --stage 4 --return-to 1|2|3|4 --message TEXT`. Keep the rejected artifact and decision in the ledger. Revise affected reports, rerun their checks, refresh later reports that depend on them, and obtain fresh Agent and human or explicitly delegated reviews before advancing. Inspect the ledger with `workflow status` after each decision and before each transition.
