# Step 3 Host-Agent Contract: Result-Driven Analysis

The static Step 3 workflow creates a source-bound analysis draft. It helps a host agent work backward from requested results, record candidate paths and unknown boundaries, and prepare a reviewable implementation plan. Static preparation, field, dependency, plan, query, trace, check, and report commands do not calculate Excel formulas or prove numerical equivalence. Python generation is a separate Stage 4 action; isolated execution and native Excel reconciliation are separate Stage 5 actions. These tools do not execute VBA or call an AI model.

All authored instructions, reports, and narrative descriptions in generated artifacts must be in English. Preserve source values, formulas, names, identifiers, and immutable provenance verbatim. Only the repository-root `README.md` and `README.zh-CN.md` are approved bilingual documentation exceptions.

This contract is workbook-independent. Derive targets, worksheet names, selectors, input groups, dimensions, projection lengths, equations, and exclusions from the user's request and the current source-bound evidence. Never borrow those facts or approvals from a previous workbook. Read each tool's supported capabilities before promising execution for a new design; reusable analysis rules do not imply support for every Excel feature.

## Define the result and scenario first

Before exploring dependencies, write down the requested result and its scenario. A target may be one value, multiple named values, a finite column or region, or an existing Step 3 field ID. For a region or field, record its physical extent and the intended order and meaning of each axis; cell geometry alone does not prove a business axis. Register targets separately when their meanings or conditions differ. Every multi-target request must declare a stable `result_order` and map each `target_id` to its result position and `shape`. If the user did not specify a layout, explicitly preserve the request order; do not sort or deduplicate results. Record the result position and shape for a single target too, and map indices within a region to their logical axes. Targets may share calculation modules, but shared dependencies must not change the result position for any `target_id`. Give targets with different meanings or conditions different IDs.

For the workflow-bound `step3.input_targets.v1` input, each target may also declare `result_kind`, `units`, and `axes`. Supply only facts stated by the user or supported by current source-bound evidence; never infer business axes from cell geometry. These fields are optional. Preserve an explicit JSON `null` when supplied, and leave an unrecorded field absent; the handoff will show either state as `Not recorded`. Copy the normalized target selection into the input catalog exactly, including its target array order and any optional metadata. Human target lists use `result_order`; the machine selection preserves its submitted array order.

```json
{
  "target_id": "annual_result",
  "selector": "Output!B2:B4",
  "result_order": 0,
  "shape": [3],
  "start_cells": ["Output!B2"],
  "result_kind": "vector",
  "units": "yearly amount",
  "axes": [{"name": "policy year", "axis_id": "policy_year", "role": "time", "keys": [1, 2, 3]}]
}
```

Bind every plan and evidence set to the selected `source_id`, `run_id`, workbook SHA-256, Step 3 binding SHA-256, scope, and current `fields` and `dependencies` hashes. Record scenario inputs explicitly, including their values or source-bound field references and applicable assumptions. A saved formula cache is an observed workbook value, never a raw input or recalculation result. Keep scenarios separate when their input sets, coverage, or branch conditions differ.

## Explore backward and maintain a path ledger

Record excluded feedback conditions in the scenario before following their paths. Cite the exact selector locations and values, the producer that depends on the requested result, and the condition that would activate the cycle. An excluded producer is not a cached external input. Static candidates may still contain it; only a source-bound active trace can establish that the selected scenario does not consume it. Do not remove dependencies or category bindings merely because a selected payout or another intermediate value is zero. State whether the generated scenario guard rejects activation. Reactivation requires a revised Step 3 design and its reviews before code generation, with an explicit feedback solver or another approved calculation boundary. Excluding one condition does not authorize any other alternative.

Read `step3 tools`, query each target with `step3 query`, then progressively use `step3 trace --direction upstream` to inspect prerequisites. Follow only the branches needed to explain the selected target. Query or trace a referenced field, range, name, or module when more evidence is needed. Retain the paths and SHA-256 values of source-bound query/trace packets.

Trace edges describe prerequisite-before-consumer structure. Present each human-readable path from the requested target backward toward its inputs, preserving every branch and its condition. Give each path a concise explanation and stable path ID. Record its target, scenario/condition, ordered fields or modules, shared dependencies, source evidence IDs, facts versus inferences, status, unresolved questions, and error handling. Shared calculations may be described once, but record which paths use them.

Treat `fields`, `dependencies`, and `execution_plan` as navigation and structural evidence only. They do not establish business meaning, logical axes, formula equivalence, or completeness. Proposed vector shapes and copied-formula families are candidates that need confirmation. A dependency trace is bounded: record every returned frontier, unresolved item, excluded-sheet boundary, dynamic/broken/unsupported reference, and truncation reason in the path ledger. Do not silently prune an unknown branch or count it as resolved. State where exploration stopped and what evidence would close the branch.

An empty `frontier` means only that the current static dependency graph traversal has no remaining nodes to visit; it does not prove runtime dependencies are closed. Even when the frontier is empty, inspect original formula text for `INDIRECT`, `OFFSET`, and other dynamic address/range construction, and for `VLOOKUP`, `INDEX`, `MATCH`, `XLOOKUP`, or other logic that may select a return row, column, or branch based on inputs. Record dynamic targets, returned columns, and conditional branches as separate paths or unresolved boundaries. If bound scenario inputs yield a finite candidate region, query it and record the scenario condition; this proves which source cells exist in that region, not that a dynamic formula accesses only that region for every input. State where exploration stopped and what evidence is still needed to close the branch.

Stop a path only at an evidenced source input, a separately declared external-input boundary, or an intentionally chosen and documented model boundary. Mark external inputs explicitly with their source/scenario binding, required values, any pending units or meaning, and the paths that consume them. Do not infer an input merely because a formula has no resolved prerequisite.

## Report handoff, closure, and implementability separately

**Documentation/handoff completeness** and **logical target closure** are different. A recorded path may contain explicit unknowns, blockers, frontiers, and missing evidence. Handoff material can still be complete when every known path unit records its current assessment, supporting evidence or reason it is unknown, gap, and next evidence needed. This status means the information is ready to hand off; it does not mean the path is understood or confirmed.

Separately report whether the selected target/scenario is closed. Call it closed within that scope only when all required branches are identified, conditions are confirmed, and every boundary has an explicit treatment. If unknown branches, dynamic references, or unconfirmed configurations remain, mark closure open/unknown. Also report whether a particular bounded option is implementable; do not call it implementable while required interfaces, dependencies, implementation boundaries, or error policies remain unconfirmed. A finite scenario may be implementable within an explicit external-input boundary even while the general-purpose model remains open.

Track these stages separately for every path and shared module:

- **Recorded/documented:** A ledger entry states the current explanation or explicit unknown, evidence/gap, and next action. This does not mean the business logic is resolved.
- **Resolved:** Evidence or human confirmation establishes the conditions, dependencies, and applicable behavior of this known path. This alone does not prove the whole target is closed.
- **Planned:** Proposed behavior and implementation boundaries are written for a declared scope.
- **Implemented:** Code implements the path and required dependencies within that scope.
- **Runtime verified:** Named test cases ran and passed under the bound scenario.
- **Blocked or unknown:** A condition, dependency, behavior, or required evidence remains unresolved.

A source formula or proposed vector is not an implementation. Code presence is not runtime verification. Never report a planned path as implemented or tested. Record case IDs, scenario bindings, expected outputs, observed outputs, and errors for runtime checks; distinguish source evidence from generated-code evidence.

Errors, missing values, and branch conditions are part of the path contract. Do not replace errors with zero, drop error rows, or assume a failed branch was unused. If an error is intentionally handled or a path is not taken for a scenario, record the explicit condition, behavior, and evidence. Keep error semantics unresolved until confirmed.

## Model variables before cell formulas

Use a logical variable as the model unit. Distinguish raw and calculated scalars, time-projection series, lookup vectors, and matrices with explicit axes. An actuarial column is a candidate time variable; confirm its time keys, range, and source label. A vertical age table is an age lookup axis, not automatically a policy-time projection. A matrix needs a meaning for both axes before grouping its columns.

Partition source extents before classifying. A column may contain unrelated scalar summaries and a separate time-projection series. A series' literal seed and calculated recurrence belong to the same logical variable. A first-period formula exception creates an equation segment inside that variable, not another model variable. Confirm these boundaries from source labels, keys, formulas, and dependencies. Preserve headers and coordinates as provenance; do not make each cell a separate model API entry.

For each variable record `variable_id`, raw/derived role, kind, logical axes and shape, source extents, storage-index mapping, demanded indices for the target, initialization, equation segments, dependencies and time lags, branch/error policy, and output use. Distinguish a variable's full source extent from the subset required by the target. Do not rebuild unused columns merely because they are next to required variables.

Declare each variable's boundary periods separately, including any time-zero seed and terminal period. Related variables can have different starting keys and lengths. A seed and its later equations are one time variable. Derive these keys and lengths from the current source; align variables by their logical period keys rather than assuming index0 represents the same period in every array.

Group equation families only after checking every relevant source member, including first/last periods and formula-local error handling. Identical translated formula text is structural evidence, not proof of business meaning or semantic equivalence. Build recurrence groups from lagged dependencies; use prerequisite order for same-period dependencies. Independent variables/categories may share arrays or loops only when their axes and ordering agree.

The Step 3 deliverable must explain how named variables and equation families become compact functions, loops, and reductions. A list of cell expressions alone does not satisfy a request for a readable modular model. Preserve unusual source references, nonlinear terms, and period-specific error behavior instead of silently correcting them. Record exact source evidence and any proposed correction as a separate decision requiring review.

For a modular model, submit an Agent-authored `step3.semantic_map.input.v1` to `step3 plan --semantic-map INPUT.json`. Bind its source/run/binding and current `fields`/`dependencies` hashes; hash-reference the source-family profile and active trace; define variables, modules, equation families, source-family mappings, and array instances. Each array instance must cite the active ordinary anchor's `anchor_source_family_id`; map its full shape and logical axes while treating active followers as the demanded subset recorded by the trace. The command writes `semantic_plan.json` and `.md`. Then run `step3 check --semantic-plan PLAN.json`; it rechecks the map and evidence hashes, exact ordinary formula-family membership, array anchors and follower subsets, shapes, and coverage, and writes `semantic_check.json` and `.md`. The mapping must assign every active ordinary formula and array follower exactly once. Source profile candidates may be grouped into one equation family, but each source-family ID must be assigned once. Declare a nonempty `index_mapping` for every source family, an explicit initial-condition field (which may be null), equation segments, dependencies, error policy, and output usage for each variable. A matrix must declare two logical axes; physical shape and source orientation remain distinct from business meaning.

The semantic check establishes exact address bookkeeping against the hash-bound profile and active trace. It does not prove that an equation-family assignment, logical axis, recurrence, or module is semantically correct. Keep `generation_ready`, `runtime_verified`, and `native_reconciled` false until their separate workflow stages pass. Add both semantic artifact hashes to `analysis.artifacts` in the `step3.report` input; a modular report can set `semantic_mapping_required: true` to require them. Stage 3 packages static evidence only and never evaluates formulas or uses formula caches.

## Offer bounded implementation options and honest coverage

When asked for options, compare them against the same targets and scenarios:

1. Implement the full set of currently supported configurations and outputs, listing unsupported or unknown branches separately.
2. Deliver one fixed, explicitly bound scenario with its complete requested target set.
3. Deliver modules or paths in stages, naming each stage's dependencies and cumulative unique work.
4. Set an explicit external-input boundary and state which outputs and paths remain inside it.

Do not call a partial region, single scenario, or staged slice a complete general-purpose model. State each option's scope, exclusions, required confirmations, error policy, and uncovered behavior. Implementation options are planning text; the current CLI does not generate or rank them.

Every coverage report must state its numerator, denominator, unit, scope, and stage. For the known-path ledger, use **known path units** as the denominator and label the measure **known-only**:

- **Documented-ledger coverage:** known path units with a complete ledger entry / registered known path units. An entry may explicitly record an unknown or blocker; this ratio does not mean the logic is understood.
- **Resolved coverage:** known path units with confirmed conditions, dependencies, and applicable behavior / the same known-path denominator. Unknown units do not enter the numerator.
- **Planned, implemented, and runtime-verified coverage:** report planned path counts, implemented path counts, and passed path/test-case counts separately. List the path IDs in each numerator; never substitute one stage for another.
- **Shared modules:** track against a separate unique-module denominator. Do not count a shared dependency once per path or repeat it in cumulative stages.

If the denominator covers known paths rather than all possible paths/configurations, label every percentage accordingly. Unknown branches and unconfirmed configurations make full-model/full-configuration coverage **unknown**. Do not convert unknown into a percentage or claim full logical closure from a known-only ratio.

## Use the existing draft sections without claiming semantic proof

The optional input `step3.model_spec.input.v1` has seven sections: `field_roles`, `logical_axes`, `calculation_groups`, `outputs`, `macro_workflow`, `open_questions`, and `validation_plan`. Label exact source/structural facts `fact`, interpretations `inferred`, and unresolved items `pending`. Use `details` for structured target IDs, path IDs, scenario bindings, option IDs, axes/shapes, and coverage records. If `details.field_ids` is present, it must cite delivered field IDs. Put unanswered units, branch conditions, axis meaning, error behavior, and missing evidence in `open_questions`.

`step3 check --spec INPUT.json` checks source/stage bindings, packet hashes, exact facts, and whether cited evidence was delivered. It does not decide whether a business interpretation, target, path, option, coverage statement, or test expectation is semantically correct. Step 3 does not establish runtime, generation, or GPU readiness. Apply the active workflow's review policy to those decisions; the input-boundary checkpoint always retains actual human review.

## Confirm the input boundary before final design

For a workflow-bound conversion, submit the reviewed target and input catalog before writing the final semantic design:

```text
step3 input-catalog --analysis DIR --workflow DIR --targets TARGETS.json --catalog CATALOG.input.json
```

The catalog groups exact source coordinates into logical scalars, vectors, and sparse or dense tables. It separately records logical object counts, fields or curves, table-mapped coordinates, source coordinates, axis metadata, adapter labels, source constants, and unresolved raw-source records. Keep source header text as metadata; do not turn each physical cell or label into a business variable. Sparse tables must show their exact coordinate map and say when row positions are physical worksheet positions rather than confirmed business records. Exclude formula cells from raw inputs and preserve literal-zero or blank source boundaries as explicit source constants only when source evidence supports that classification.

Bind the catalog to the exact source, run, workbook SHA-256, current analysis binding, target order, and saved scenario. This input-catalog phase describes the saved source only; it does not accept scenario overrides or external numeric values. `scenario.overrides` must be an empty object, and selectors must be a map of names to text metadata. Source, scenario, target, and catalog objects use closed documented field sets. `value_source_policy` must keep `formula_cache_allowed` false; any declared raw-source origin must be the text `formula_mode workbook source`, and formula-derived values must remain unavailable now. Future-source and binding declarations must be non-empty text lists using the declared policy values. An object-form open question requires non-empty text `question_id` and `question`; any supplied `source_records[].open_question_id` must also be text and cite a declared question. Axis provenance descriptions and source labels are text metadata. Reject unrecognized fields or wrong-typed values such as `sample_rates`, `rates`, structured availability flags, or numeric selector arrays instead of persisting them. Preserve source labels verbatim in their documented metadata fields. Formula-derived external values are unavailable until a later, separately approved value-capture design is implemented and bound. Never use formula caches as inputs.

Topology evidence is optional for this checkpoint. Without a current target-bound trace, mark target reachability, formula closure, dynamic branches, lookup-selected inputs, and coverage as unknown. A historical trace may be listed as a lead but cannot prove the current boundary. Reconcile older candidate coordinates absent from the current fields against the source; distinguish stored-but-empty cells from missing cells and keep blank-read semantics open if a later formula consumes them.

Review the input-boundary artifact separately from the final Step 3 design. This checkpoint always requires both an independent Agent decision and an actual human decision on the exact JSON/Markdown pair, even when a workflow has a TypeSafe delegation. A TypeSafe receipt may be retained as a separate recommendation, but it cannot approve or reject this checkpoint and never supplies the human decision. Approval records `input_boundary_confirmed` and keeps Stage 3 next; it does not approve the final design or release Step 4. The separate final-design review and later Stage 4–6 reviews keep the workflow's ordinary Agent+human or explicitly delegated Agent+TypeSafe policy.

After the catalog has both required input-boundary decisions, make a fresh continuation analysis directory with the same source binding and current fields/dependencies/structural-plan hashes. Do not add semantic-plan/check stages to the analysis.json that the accepted input-boundary revision directly binds; semantic writes belong in the continuation directory. The accepted boundary remains separately hash-checked against its original files.

For a first-use workbook without Step 4 history, run `step3 source-trace --analysis DIR --workflow DIR --out DIR`. This writes the separate `gp.source_candidate_trace.v1` artifact from the canonical inventory and confirmed input catalog. It includes both readable conditional arms, preserves formula-derived external cuts as formula-text/hash provenance, stops before their prerequisites, and records raw candidates as reached, not reached in the known graph, or unresolved/possibly reached. Lookup-selected rows, dynamic/broken/unsupported references, upstream exclusions, arrays, and expansion caps remain explicit unknowns. No formula values, formula caches, or Excel are read; the artifact does not establish active closure or release Step 4.

An Agent may also provide `--model-scope INPUT.json` to fence a candidate analysis to finite source-coordinate regions. Use `gp.source_model_scope.input.v1` with the current `source`, `scenario`, `targets`, `analysis`, and `input_boundary` objects copied from the current unscoped candidate trace; include `full_candidate_trace: {path, sha256}`, `allowed_regions: [{source_ref, rationale}]`, and `proposed_formula_starts: [{source_ref, rationale}]`. The full trace and scope file are both checked by hash. Every confirmed formula-derived input cut and every target start must be inside the fence. Proposed formula starts must be canonical formula cells inside the fence, distinct from target starts, and are separate candidate roots, not active paths. Broad and whole-row/column references are intersected with the allowed regions before expansion; omitted coordinates become deduplicated scope frontiers containing the referring formula and hash, original reference text, excluded extent, and coordinate count. A fence cannot imply omitted formulas are unused. Scoped traces use `candidate_scope: scope_bounded_static_candidate_design`; profile, semantic plan/check, and Stage 3 report bind the scope hash directly. Any changed scope or evidence requires rebuilding downstream artifacts. Closure, active coverage, generation readiness, runtime verification, and native reconciliation remain unknown or false.

Use `step3 profile --analysis DIR --source-trace SOURCE_CANDIDATE_TRACE.json --out DIR` for the candidate profile. The existing `step3 profile --analysis DIR --trace ACTIVE_TRACE.json --out DIR` remains the Step 4 active-trace route. Supply exactly one of `--trace` and `--source-trace`. A candidate semantic map declares `selection_basis: static_candidate`, cites both the candidate profile and `source_candidate_trace`, and uses role `external` plus the exact confirmed `boundary_variable_id` for each formula-derived external vector. External extents, dimensions, and availability are checked against the accepted catalog; these positions are not mapped as local source formula families and their missing values remain blocking unknowns. For scoped traces, the semantic plan records the same `candidate_scope` and direct model-scope evidence path/SHA; the Stage 3 report rejects stale scope evidence. Candidate mapping coverage describes the candidate set only. Candidate closure, active-member coverage, generation readiness, runtime verification, and native reconciliation remain unknown or false.

## Stage gates and handoff

By default, all six stages require separate Agent and human decisions on the current JSON/Markdown artifact pair. Use `workflow status --workflow DIR` to inspect the current stage, stale inputs, decisions, and next permitted stage. Record Agent or human reviews with `workflow confirm --workflow DIR --stage 3 --reviewer agent|human --decision approve|reject --message TEXT`; use the `human` reviewer only after an explicit user response. Route a rejection with `workflow reject --workflow DIR --stage 3 --reviewer agent|human --return-to 1|2|3 --message TEXT`. A workflow may use TypeSafe for later final-design and stages 4–6 reviews only after an explicit, matching human authorization is registered with `workflow delegate --workflow DIR --authorization AUTH.json`; this delegation does not change the mandatory Agent+human input-boundary pair above. For eligible later reviews, submit the current artifact-bound request through the live API with `workflow typesafe --workflow DIR --stage 3 --request REQUEST.json`, then import its generated `review.json` with `workflow confirm --workflow DIR --stage 3 --reviewer typesafe --decision approve|reject --message TEXT --evidence REVIEW.json`. Handwritten request/response packets are not accepted as live reviews; the CLI logs the invocation, request, response, and current artifact hashes. TypeSafe is a distinct receipt, never a human receipt. Agent review and all checks remain required, insufficient confidence is not approval, and other workflows keep the default Agent+human policy. A new artifact revision, changed upstream input, or changed authorization/request/response evidence invalidates downstream decisions.

A new explicit actual-human approval under a valid active TypeSafe delegation restores the required pair to Agent+human only for that exact current, unrejected JSON/Markdown pair and revision; it does not change the authorization or other stages. A rejection from any reviewer makes that revision ineligible for later approvals; create a replacement artifact and obtain new decisions. The input-boundary catalog always requires actual human review.

Stage 3 cannot proceed until Stage 2 is approved. `step3 report --analysis DIR --design INPUT.json --workflow DIR` creates the static analysis/design checkpoint. For each `scenario.primary_inputs` record that explicitly provides both `source_cell` and `source_literal`, the report checks that the qualified source cell physically exists, is formula-free, and matches the declared literal in the hash-bound Step 1 workbook copy. A partial assertion, missing cell, formula cell, or mismatch blocks the report before a revision is appended; mismatch diagnostics identify the scenario, selector, address, expected value, and actual value. The report includes a `scenario_source_validation` ledger of checked declarations. These checks validate authored assertions only: the tool does not infer scenario values or add undeclared guards. It does not calculate formulas, invoke Excel, generate Python, or read formula caches for numeric results. After the design receives both approvals, Stage 4 runs `step4 discover --workflow DIR` to build a fresh source-bound active trace from formula text and raw source values, then `step4 generate --workflow DIR` to emit and smoke-test a standalone Python bundle. Stage 5 separately validates that generated code, captures a fresh macro-disabled Excel baseline on a private copy, and reconciles named results and active formulas. The oracle alone does not advance Stage 5; both generated-code validation and reconciliation must pass before Stage 5 review. Stage 6 summarizes the accepted artifacts after Stages 1–5 are approved.

An optional `tool_execution_ledger` records each tool, command, purpose, text outputs, and status. These are report entries only; `step3 report` never runs the listed commands. An optional `external_value_capture_plan` states a later-stage prerequisite and its source ranges, method, binding, and validation. Keep `current_values_available` and `formula_cache_allowed` false in Stage 3. Do not include captured values or treat the plan as an approval to capture them.

Report path counts, selected branches, and feedback conditions only from evidence for the current target and scenario. An inactive condition is not a feedback solver or all-configuration closure. The Stage 4 emitter is limited to the accepted trace and supported formula subset. Unsupported active formulas, external references, cycles, and unbound runtime inputs block generation or validation. Stage 5 requires Windows with Microsoft Excel for the native oracle. None of these results imply GPU execution.

If an implementation is rejected, retain it as historical evidence and record the required return stage. Do not accept a cell-expanded bundle as a requested modular deliverable or transfer prior approval to a replacement design. Revised Step 3 and Step 4 artifacts each require fresh Agent approval and the active workflow's separately authorized human or TypeSafe decision.

Current Stage 3 commands include `step3 input-catalog`, `step3 source-trace --analysis DIR --workflow DIR [--model-scope INPUT.json] --out DIR`, and `step3 profile --analysis DIR (--trace ACTIVE_TRACE.json | --source-trace SOURCE_CANDIDATE_TRACE.json) --out DIR`, along with `step3 agent`, `step3 tools`, `step3 prepare`, `step3 fields`, `step3 dependencies`, `step3 plan [--semantic-map INPUT.json]`, `step3 query`, `step3 trace`, `step3 check [--semantic-plan PLAN.json]`, and `step3 report`. Without a semantic map, `step3 plan` orders structural dependency blocks; it is not a result-target plan. Dedicated commands for automatically discovering business targets or determining semantic axes are not implemented. Maintain the target/path/options ledger as source-cited design evidence and record unknowns rather than guessing.

For a first-use source-only flow, use `step3 source-trace` and then `step3 profile --source-trace`; both require the confirmed catalog and current continuation analysis, but no historical Step 4 trace. The profile compares candidate formula text with the canonical Step 1 inventory and groups identical translated syntax. It does not read trace values or formula caches, calculate formulas, decide business families, or establish active closure. For an already discovered workbook, `step3 profile --trace` retains the historical/current Step 4 active trace contract. In either mode, the resulting profile is an input to `step3 plan --semantic-map INPUT.json`; array followers still need explicit shape mappings.

Use only the bound workbook and evidence artifacts. Do not edit the source Excel, Step 1/2 artifacts, existing model structures, or formula caches. A handoff draft is ready when every requested target has a path ledger or an explicit unknown/blocked boundary, option scopes are clear, coverage denominators are stated, and remaining decisions are ready for human review. Handoff completeness does not mean the target is closed or implementable. Report incomplete evidence and source locations instead of guessing.

## Shared workflow and decision order

Treat `input/` as the source Excel area and `output/` as the home for each new source-bound workflow and its reports. Start a new conversion from the current workbook and user request; never carry case facts or approvals from another workbook or run.

Read `stepN tools` and choose the existing actions that answer this case's open questions. Explore from the source and current bound evidence, inspect each action's checks and outputs, then prepare the paired machine-readable JSON and reader-facing Markdown handoff. Review all files named in the handoff and confirm their source and upstream bindings before asking for a decision. Do not continue when a required check fails or an input is stale.

Before entering a stage, run `workflow status` and verify that the stage is currently permitted and every required upstream decision and artifact is current. A successful tool check, report creation, draft CLI action, or clarification does not itself approve a stage or advance the workflow. Keep legacy standalone source-exploration APIs available for discovery; they do not create a workflow approval.

The default review order is Agent first, then the actual human. Record the Agent decision against the exact current JSON/Markdown pair with `workflow confirm`; present that pair and its practical limits to the user; record a human approval only after an explicit response. New TypeSafe approvals also require a current matching Agent approval. Use TypeSafe only under a valid, explicitly scoped authorization already registered for this workflow; never infer or transfer delegation. The Step 3 input-boundary checkpoint always requires an actual human decision.

Ask the user when target, scope, input kind, axis, units, or business interpretation is materially unresolved. Keep unknown facts marked as unknown; do not turn planning into measured execution or claim checks that did not run.

When a reviewer rejects a report, route it to the current or an earlier responsible stage with `workflow reject --return-to`. Keep the rejected artifact and decision in the ledger. Revise affected reports, rerun their checks, refresh later reports that depend on them, and obtain fresh Agent and human or explicitly delegated reviews before advancing. Inspect the ledger with `workflow status` after each decision and before each transition.
