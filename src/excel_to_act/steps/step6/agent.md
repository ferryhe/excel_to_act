# Step 6 Agent Contract: Final Conversion Report

Step 6 summarizes the accepted source, index, design, generated implementation, and validation/reconciliation reports. It does not calculate formulas or upgrade a saved-scenario result into all-configuration coverage.

For the reusable final-report writing and review scaffold, see the [Excel-to-Act Step 6 skill](excel-to-act-step6/SKILL.md), or print it with `excel-to-act step6 skill`. Print its Markdown scaffold with `excel-to-act step6 template`. The CLI renderer and its JSON evidence remain authoritative for generated reports.

The Markdown report is the human handover. Start with the result table in accepted target order and the scoped conclusion, then review purpose and scope, source inputs and assumptions, calculation order, conversion approach, validation, limitations, handover instructions, and acceptance state. It should use accepted target names, ordering, units or basis, scenario literals, input-catalog totals and source-tab counts, field-group shapes and time alignment, recurrence notes, execution order, and shared-module responsibilities. The module flow summarizes accepted design data; it is not implementation proof by itself.

If the accepted design links an input-boundary catalog, confirm that the recorded digest matches and that Step 6 binds the catalog files in its own input-file list. If the catalog is missing or stale, the report must say those catalog facts are unavailable. Do not infer missing source counts, axes, inputs, or business meanings.

Keep current result values and scoped conclusions in the report body. Explain the recorded standalone-Python and native-workbook validation methods, comparison denominators, partial source extraction, and actual unresolved business interpretations when those facts are present. Do not put raw JSON/list dumps or SHA strings in the main body. Detailed input literals and locations, hashes, review receipts, prior options, preserved formula notes, and original design questions belong in appendices. Preserve question text and dispositions in JSON; later capture and native-comparison evidence may answer an execution prerequisite without changing that historical record. Do not turn an old planning statement into a current execution claim.

Include only Step 5 route IDs supported by matching native comparisons. Keep condition-only checks separate from numerical paths; an inactive feedback condition does not mean a feedback solver exists. This handover does not claim actuarial certification or compliance with a professional standard.

Write new instructions, report narration, and generated artifact prose in English. Preserve source values, formulas, identifiers, and immutable provenance verbatim. Only the repository-root `README.md` and `README.zh-CN.md` are approved bilingual documentation exceptions.

Read `step6 tools` and confirm that Stages 1–5 are current and approved. Run `step6 report --workflow DIR`. Review `conversion_report.json/.md` for source-quality limits, Step 3 planning history, Step 4 generated path IDs, and only the Step 5 route IDs supported by native comparisons. Review the saved-scenario target values, code bundle/run command, exclusions, and open questions. Keep condition-only checks separate from numerical paths; an inactive feedback condition does not mean a feedback solver exists. A partial slice must not be called a complete general-purpose model; all-configuration coverage stays unknown unless supported by evidence.

Record the Agent decision only after checking the exact report pair and references. The report is generated ready for review and remains immutable after acceptance; read later Agent, TypeSafe, or human decisions from the linked `workflow.json` acceptance ledger. By default, the human decision must follow an explicit user response. If this workflow has an active TypeSafe delegation, submit a current-bound request with `workflow typesafe --workflow DIR --stage 6 --request REQUEST.json`, then confirm using its generated evidence file; hand-written packets do not count as live reviews. If any accepted upstream artifact changes, refresh the affected checkpoint and every later report before reviewing them again.

A new explicit actual-human approval under a valid active TypeSafe delegation restores the required pair to Agent+human only for that exact current, unrejected JSON/Markdown pair and revision; it does not change the authorization or other stages. A rejection from any reviewer makes that revision ineligible for later approvals; create a replacement artifact and obtain new decisions.

## Shared workflow and decision order

Treat `input/` as the source Excel area and `output/` as the home for each new source-bound workflow and its reports. Start a new conversion from the current workbook and user request; never carry case facts or approvals from another workbook or run.

Read `stepN tools` and choose the existing actions that answer this case's open questions. Explore from the source and current bound evidence, inspect each action's checks and outputs, then prepare the paired machine-readable JSON and reader-facing Markdown handoff. Review all files named in the handoff and confirm their source and upstream bindings before asking for a decision. Do not continue when a required check fails or an input is stale.

Before entering a stage, run `workflow status` and verify that the stage is currently permitted and every required upstream decision and artifact is current. A successful tool check, report creation, draft CLI action, or clarification does not itself approve a stage or advance the workflow. Keep legacy standalone source-exploration APIs available for discovery; they do not create a workflow approval.

The default review order is Agent first, then the actual human. `workflow confirm` records approvals only; use the stage-specific `workflow.reject` command and its explicit `--return-to` route to reject. Record the Agent decision against the exact current JSON/Markdown pair with `workflow confirm`; present that pair and its practical limits to the user; record a human approval only after an explicit response. New TypeSafe approvals also require a current matching Agent approval. Use TypeSafe only under a valid, explicitly scoped authorization already registered for this workflow; never infer or transfer delegation. The Step 3 input-boundary checkpoint always requires an actual human decision.

Ask the user when target, scope, input kind, axis, units, or business interpretation is materially unresolved. Keep unknown facts marked as unknown; do not turn planning into measured execution or claim checks that did not run.

When a reviewer rejects a report at Stage 6, route it to the current or an earlier responsible stage with `workflow reject --workflow DIR --stage 6 --return-to 1|2|3|4|5|6 --message TEXT`. Keep the rejected artifact and decision in the ledger. Revise affected reports, rerun their checks, refresh later reports that depend on them, and obtain fresh Agent and human or explicitly delegated reviews before advancing. Inspect the ledger with `workflow status` after each decision and before each transition.
